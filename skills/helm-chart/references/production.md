# Compatibility and production operation

## Declare the support boundary

Use `Chart.yaml` `apiVersion: v2` for Helm 3 and 4 consumers. Chart `version` identifies the package. A quoted `appVersion` identifies the application. Set `kubeVersion` to a SemVer constraint justified by the APIs and fields used, upstream dependencies and the tested range. Verify boundary versions, including provider-specific prerelease suffixes if supported. Independently check the Helm minor's Kubernetes skew table. For optional CRDs, model the feature as a value and check the exact group/version/kind in discovery when needed. Test offline renders with explicit `--kube-version` and `--api-versions`. A matching discovery entry alone says nothing about controller health. [Chart specification](https://helm.sh/docs/topics/charts/) · [Helm 4 overview](https://helm.sh/docs/overview/) · [Helm skew policy](https://helm.sh/docs/topics/version_skew/)

For charts with dependencies, resolve intentional changes with `helm dependency update CHART` and review the resulting `Chart.lock`. Build CI artifacts with `helm dependency build CHART` from the committed lock. A missing lock makes that command resolve versions again. Package and promote the tested artifact by immutable identity. [Dependency build](https://helm.sh/docs/helm/helm_dependency_build/) · [OCI registries](https://helm.sh/docs/topics/registries/)

## Choose workload behavior

| Condition | Chart design and test |
| --- | --- |
| An upgrade must preserve workload identity | Keep Deployment selector labels stable and equal to a subset of Pod labels. Put chart versions, image versions and other changing metadata outside the selector. Verify the Service selects Pods from this release when another release shares the namespace. [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) |
| Traffic must survive rollout or node maintenance | Size replicas, `maxSurge` and `maxUnavailable` for actual capacity. A PDB governs voluntary evictions through the Eviction API. Set exactly one of `minAvailable` and `maxUnavailable`, match a specific workload and test a drain. A single replica with `minAvailable: 1` can block maintenance. Topology spread needs eligible nodes in each domain. [Disruptions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/) · [Topology spread](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/) |
| Startup may be slow or dependencies may fail | Let readiness report whether the instance should receive traffic. Use a startup probe sized to measured cold start. Use liveness for a local failure that a restart can repair. Test dependency outages, shutdown and readiness transitions. [Pod probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/) |
| An HPA owns scale | Omit the fixed workload replica count while autoscaling is enabled. For an existing release, stage the ownership transfer to avoid a transient scale-down. Check the metrics provider, resource requests for utilization targets and scheduling headroom at peak. Choose requests and limits from workload measurements. [Horizontal Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) · [Resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) |
| Storage must survive release changes | Support an existing claim when storage is managed independently. Record ownership, storage class, access modes, StatefulSet claim retention and underlying PV reclaim policy. Verify data persistence through upgrade and a restore from backup before promising recovery. [Persistent volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/) · [StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/) |

## Observe rollout health

Expose an application-specific readiness signal and emit structured logs to stdout or stderr. Establish rolling error rate, latency, saturation, restart and ready-replica thresholds against a known healthy revision. Compare during rollout, including termination under traffic. Size the grace period for connection draining and process shutdown; a preStop handler consumes that same budget. Use instrumented application metrics when available. Gate a ServiceMonitor on the installed monitoring API and verify that its selector and named Service port produce a discovered, healthy scrape target. A monitor object alone provides no telemetry. [Termination lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination) · [Logging architecture](https://kubernetes.io/docs/concepts/cluster-administration/logging/)

## Expose traffic deliberately

Keep a namespaced Service as the backend. Retain an existing Ingress contract when required. For Gateway API, make the HTTPRoute optional and document the required CRDs, compatible controller, Gateway listener and backend Service port. Platform teams commonly own the GatewayClass and shared Gateway. Route-to-Gateway attachment across namespaces needs a matching listener `allowedRoutes` policy. A cross-namespace backend reference needs a ReferenceGrant in the backend namespace. Check `Accepted` and `ResolvedRefs` for the intended Route parent at the current generation, then send a request through the Gateway. [Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/) · [HTTPRoute](https://gateway-api.sigs.k8s.io/reference/api-types/httproute/) · [Cross-namespace attachment](https://gateway-api.sigs.k8s.io/guides/user-guides/multiple-ns/) · [ReferenceGrant](https://gateway-api.sigs.k8s.io/reference/api-types/referencegrant/)

## Rehearse release transitions

1. **Start with a published predecessor.** Install it in a disposable namespace on a representative cluster with realistic values and synthetic state. Upgrade the same release to the candidate. Check immutable fields, endpoints, permissions, mounted data and application behavior. Include a migration path for resources using API versions removed by the target cluster. [Deprecated Kubernetes APIs](https://helm.sh/docs/topics/kubernetes_apis/)
2. **Exercise the actual apply method.** Helm 4 defaults to server-side apply for new releases. Upgrades and rollbacks normally retain the previous release's method, so a Helm 3 release keeps client-side application after the client changes. Inspect `metadata.managedFields` on conflicts and assign each disputed field to its intended owner. Rehearse explicit transitions separately. [Helm 4 overview](https://helm.sh/docs/overview/) · [Server-side apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/)
3. **Check rollback feasibility before automating it.** Helm 3 uses `helm upgrade --atomic`. Helm 4 names the upgrade option `--rollback-on-failure`. Set a timeout appropriate to start-up and migrations. Select a known revision with `helm history RELEASE`. Exercise `helm rollback RELEASE REVISION --wait` in the test environment. Database writes, persistent data and hook side effects need their own recovery plan. Use backward-compatible migrations or a tested restore or forward-fix procedure. [Helm 3 upgrade](https://helm.sh/docs/v3/helm/helm_upgrade/) · [Helm 4 upgrade](https://helm.sh/docs/helm/helm_upgrade/) · [Rollback](https://helm.sh/docs/helm/helm_rollback/)
4. **Assign CRD and hook ownership.** Native Helm installs raw YAML in `crds/` ahead of ordinary resources, skips existing definitions and leaves their update and deletion to an explicit owner. A dry-run cannot register a new type. Establish CRDs on a disposable cluster before validating their instances. Coordinate served/storage versions, stored-object migration and conversion webhook availability. For hook Jobs, choose bounded retries, idempotent work and explicit deletion policy or TTL. Check expected artifacts after uninstall. [CRDs](https://helm.sh/docs/chart_best_practices/custom_resource_definitions/) · [CRD versioning](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning/) · [Chart hooks](https://helm.sh/docs/topics/charts_hooks/)

## Match the GitOps reconciler

Argo CD uses Helm to render manifests and owns sync, health and pruning. Check supported hook mappings, render twice to detect drift and recover by reverting the desired chart/values revision. Flux helm-controller manages Helm release actions. Review the installed controller's remediation, drift detection, test and install/upgrade CRD policies. Flux `CreateReplace` can update existing definitions and requires a coordinated schema migration. Test the same controller version and policy used in production. [Argo CD](https://argo-cd.readthedocs.io/en/stable/user-guide/helm/) · [Flux HelmRelease](https://fluxcd.io/flux/components/helm/helmreleases/) · [OpenGitOps principles](https://opengitops.dev/)
