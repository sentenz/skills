# Patterns from the device example

Read this reference when adapting device interfaces, paired flows, trust boundaries, or
interaction-specific STRIDE threats. Use `assets/example-minimal.tm7` as the generation
baseline. Consult `references/Example_Threat_Model.tm7` for modeling patterns, not as a
replacement serialization template. Paths here are relative to the skill directory.

## Select a pattern

The device example contains one drawing surface, eight components, two boundary shapes,
ten directed flows, and fifty threats spanning all six STRIDE categories.

| Pattern | Evidence in the example | Adaptation |
| --- | --- | --- |
| Components | MCU and position sensor as processes; flash memory with bootloader as a data store; debug probe, operator, PLC/DCS, and UPS as external interactors | Select shapes by the component's role within the modeled system. Retain only components supported by the target architecture. |
| Bidirectional interfaces | Separate MCU-to-debugger and debugger-to-MCU JTAG flows; separate MCU-to-NVM and NVM-to-MCU QSPI flows | Create one connector per direction with distinct UUIDs, labels, and endpoint references. Assess each direction independently. |
| Distinct human interactions | Operator-to-MCU pushbuttons and MCU-to-operator LED status | Separate command input from status output; describe the actual information and interface. |
| Physical dependencies | UPS supply, two-wire 4–20 mA power/signal, and a motion interaction | Include physical dependencies only when relevant to scope. Confirm direction and security meaning from the architecture rather than inferring them from the sample label. |
| Trust and scope | `Trust Boundary Example Device` and `Out of Scope` boundary shapes | Place boundaries around the intended trust domains. Record scope decisions and reasons explicitly; a boundary named `Out of Scope` is only a label. |

For border boundaries, both bundled catalogs define `GE.TB.B`; use it for both
`GenericTypeId` and `TypeId` with `i:type="BorderBoundary"`. The catalogs also define
`GE.TB.L` for line boundaries; do not substitute the undefined `GE.TB`.

## Adapt threats to the interaction

Use the sample's threats as review prompts. All fifty have `State=AutoGenerated` and
priority `High`; these values do not establish applicability, severity, or completed mitigation.

For example, the PLC-to-MCU two-wire interaction includes spoofing, repudiation, data-flow
sniffing, interruption, and elevation-of-privilege candidates. Confirm whether the actual
interface carries identities, sensitive data, or executable commands before retaining those
candidates. Do not assume a remote-code-execution threat or an encryption recommendation
applies to an analog interface merely because the generated example includes it.

1. Identify the source, flow, target, and affected asset for each candidate.
2. Write an architecture-specific `UserThreatDescription` and feasible `PossibleMitigations`
   in the existing threat property collection. Keep the STRIDE category aligned with the threat.
3. Select a threat type from the baseline KnowledgeBase by its definition, not by a matching
   name or category alone. If no suitable type exists, flag the gap rather than inventing an ID.
4. Set priority and state from the assessment. Do not copy the minimal template's `Mitigated`
   state or its claim of implemented MFA/PIM controls into a new assessment.
5. Rebuild the threat dictionary key as `TypeId + SourceGuid + FlowGuid + TargetGuid`, and
   `InteractionKey` as `SourceGuid:FlowGuid:TargetGuid`. Keep these consistent with the threat
   fields, the referenced drawing surface, and the intended interaction.

## Serialization differences

These are observations from the bundled XML files, not proof of compatibility across tool versions.

| Detail | Minimal template | Device example | Generation rule |
| --- | --- | --- | --- |
| KnowledgeBase manifest | Azure Threat Model Template, `1.0.0.33` | SDL TM Knowledge Base (Core), `4.1.0.11` | Retain the baseline catalog. Check generic and standard element IDs as well as threat IDs before adapting a block. |
| After `ThreatInstances` | Root `ThreatMetaData`, then `KnowledgeBase`, then `Profile` | `ThreatGenerationEnabled`, `Validations`, `Version` (`4.3`), then `KnowledgeBase`, then `Profile` | Preserve the baseline root sequence. Do not splice in the example's version fields. |
| Threat identifiers | `TH117` | IDs such as `S2`, `E7`, and `D4` | Use IDs from the output's catalog and rebuild keys accordingly. |
| Threat state | One `Mitigated` threat | Fifty `AutoGenerated` threats | Reassess state and supporting evidence for the target system. |
| Object reference IDs | Present on the surface, stencils, connector, and KnowledgeBase | Present on the surface, stencils, connectors, and KnowledgeBase | Preserve existing reference tracking and allocate unique IDs when cloning blocks. Neither example puts `z:Id` on every XML object. |

Both files contain a top-level `KnowledgeBase` and a separate `ThreatMetaData` collection
inside that catalog. Do not confuse catalog metadata with the minimal template's root-level
`ThreatMetaData` element.

The minimal template's threat reverses the endpoints of its connector and retains an
`InteractionString` unrelated to the connector's `Send Payload` label. Its GUIDs resolve,
but this is not sufficient evidence of semantic consistency. Reconcile endpoints, labels,
and threat descriptions with the intended interaction when adapting it; leave the source
asset unchanged.

The existing no-declaration, compact-output, and namespace conventions remain the generation
policy. These examples alone do not prove that alternative whitespace or equivalent namespace
prefixes cause deserialization failure. Preserve the baseline conventions and report actual
tool-open results separately; do not infer a tool release from the example's `Version` field.

## Inspect only what is needed

Parse the XML rather than printing either complete file into context. Both contain large
embedded catalogs and image data. Bind namespaces by URI and select:

- `DrawingSurfaceList/DrawingSurfaceModel/Borders` and `Lines` for shapes and connectors.
- `ThreatInstances` for candidate threats and their GUID references.
- `KnowledgeBase/GenericElements`, `StandardElements`, and `ThreatTypes` to resolve IDs.
- `KnowledgeBase/Manifest` and root child names to compare template variants.

Before delivery, check UUID validity and uniqueness, dictionary-key/GUID agreement, unique
`z:Id` values and resolved `z:Ref` values where present, connector endpoints, threat references,
catalog membership, and threat/interaction-key construction. Review scope, flow direction,
and mitigation claims separately. Only report Microsoft Threat Modeling Tool compatibility
as tested after an actual open/save check in that application.
