## Architecture and interfaces

| Example component | Shape and type | Transferable pattern |
|-------------------|----------------|----------------------|
| MCU | `StencilEllipse`, `GE.P` | Model a firmware execution context as a generic process. |
| Flash Memory (NVM) with Bootloader | `StencilParallelLines`, `GE.DS` | Model persistent firmware/configuration storage separately. |
| Debug Probe; PLC / DCS | `StencilRectangle`, `GE.EI` | Represent external equipment and debug access as actors. |
| Operator | `StencilRectangle`, `SE.EI.TMCore.User` | Use a specialized actor only with its matching catalog properties. |
| Magnetoresistive Position Sensor; Control Valve / Actuator | `StencilEllipse`, `GE.P` | Preserve the example's representation when inspecting it; choose target shapes and scope from actual behavior. |
| Uninterruptible Power Supply (UPS 12-36 V DC) | `StencilRectangle`, `GE.EI` | Retain relevant physical dependencies even when excluded from analysis. |
| Trust Boundary Example Device; Out of Scope | `BorderBoundary`, `GE.TB.B` | Distinguish visual grouping from property-based scope exclusions. |

The connectors demonstrate these interface patterns:

| Interface | Directed connectors | Adaptation |
|-----------|---------------------|------------|
| JTAG | MCU → Debug Probe; Debug Probe → MCU | Assess readout and debug commands independently. |
| QSPI | MCU → NVM; NVM → MCU | Distinguish writes from firmware/configuration reads. |
| Two-wire 4–20 mA | PLC / DCS → MCU | State the signal and power assumptions; add another direction only if justified by the target architecture. |
| Local controls and indication | Operator → MCU via pushbuttons; MCU → Operator via LED status | Keep input and observable output separate. |
| Sensor bus | Sensor → MCU via I2C | Reassess scope for the actual electronic interface. |
| Power | UPS → MCU | Preserve the dependency and justify exclusion where appropriate. |
| Mechanical interaction | Sensor → Actuator | Review the physical meaning and direction rather than treating it automatically as software traffic. |

Do not infer missing control or response flows. The example is a source of patterns,
not a complete specification for every device using these interfaces.

## Typed properties and scope

Clone the complete property block before editing its value. Keep `DisplayName`, `Name`,
the typed `Value`, and any `SelectedIndex` in their original namespaces and order.

For example, the MCU's `Code Type` is a `ListDisplayAttribute` with these ordered
options and a selected index of `2`:

| Index | Option |
|-------|--------|
| 0 | `Not Selected` |
| 1 | `Managed` |
| 2 | `Unmanaged` |

For a flow, `Source Authenticated` has `Not Selected`, `No`, `Yes`, and selects `1`
(`No`). `Destination Authenticated` has only `No`, `Yes`, and selects `0` (`No`).
Read each option array before selecting an index. Do not carry example authentication,
sanitization, confidentiality, or integrity settings into another system without evidence.

`Out Of Scope` is a BooleanDisplayAttribute with a Schema boolean value;
`Reason For Out Of Scope` is a separate StringDisplayAttribute. The example marks the
sensor, power supply, and actuator out of scope. It also marks the sensor-to-MCU and
power-to-MCU flows out of scope. Those flags are independent of the trust borders.

Use these observations to improve the target model:

- Document a reason for every excluded component and flow. The example's excluded I2C
  flow has an empty reason; do not reproduce that omission.
- Reassess claims of passive behavior. An interface labeled I2C or a component labeled
  sensor does not by itself establish that electronics or firmware are outside scope.
- Review connectors touching excluded endpoints. The mechanical connector is not itself
  flagged out of scope, although both endpoints are; make the target scope decision explicit.
- Keep exclusions visible as assumptions so later reviews can revisit them.

## Threat records

The first threat illustrates the linkage between a generated threat and a concrete
interaction. Use these values to locate the record, not as identities for a new model:

| Field | Example value |
|-------|---------------|
| Catalog `TypeId` | `S2` |
| Numeric threat `Id` | `183` |
| `SourceGuid` | `2c04f557-30f1-4fde-9527-2b190e6b2d7c` (Operator) |
| `FlowGuid` | `9ac0f863-3849-4fe2-befd-fa32dce6fea1` (pushbuttons) |
| `TargetGuid` | `b12efa5e-d565-4d97-970c-0f16f0efcdbe` (MCU) |
| `Title` property | `Spoofing the MCU Process` |
| `UserThreatCategory` property | `Spoofing` |
| `State` | `AutoGenerated` |

The Arrays dictionary key starts with `S2` followed immediately by source, flow, and
target UUIDs. `InteractionKey` contains the three UUIDs separated by colons.
`DrawingSurfaceGuid` points to the surface in the inventory above. Preserve the
`KeyValueOfstringThreatpc_P0_PhOB` wrapper spelling.

Keep the display properties separate from the similarly named nil members on the
threat object. The example's property dictionary contains:

```text
Title
UserThreatCategory
UserThreatShortDescription
UserThreatDescription
InteractionString
Priority
```

Use `UserThreatDescription` for a concrete attack and impact. Keep `InteractionString`
aligned with the modeled flow name. Preserve catalog category spellings and use only
threat types present in the selected `ThreatTypes` collection. Do not transplant Core
identifiers such as `S2` or `E7` into the minimal Azure template's `TH...` catalog.

Review generated suggestions against physical and protocol capabilities. A generated
remote-code-execution threat on a 4–20 mA signal is a hypothesis requiring an actual
input-processing attack path, not an established vulnerability. Record proposed controls
using fields supported by the catalog; use the supported justification field for review
decisions. Retain `AutoGenerated` until an evidence-based review changes its state.

## Inspect relevant subtrees

Use namespace-aware extraction to inspect the large single-line export without copying
its catalog into the prompt. Run from the skill directory:

```bash
python - <<'PY'
import xml.etree.ElementTree as ET
from pathlib import Path

ns = {
    'm': 'http://schemas.datacontract.org/2004/07/ThreatModeling.Model',
    'd': 'http://schemas.datacontract.org/2004/07/ThreatModeling.Model.Abstracts',
    'a': 'http://schemas.microsoft.com/2003/10/Serialization/Arrays',
    'b': 'http://schemas.datacontract.org/2004/07/ThreatModeling.KnowledgeBase',
}
root = ET.parse(Path('references/Example_Threat_Model.tm7')).getroot()
print('Root order:', [e.tag.rsplit('}', 1)[-1] for e in root])
for surface in root.findall('m:DrawingSurfaceList/m:DrawingSurfaceModel', ns):
    print('Surface:', surface.findtext('d:Guid', namespaces=ns))
    for collection in ('Borders', 'Lines'):
        for entry in surface.find('m:' + collection, ns):
            value = entry.find('a:Value', ns)
            print(collection, entry.findtext('a:Key', namespaces=ns),
                  value.findtext('d:TypeId', namespaces=ns))
            for prop in value.findall('d:Properties/a:anyType', ns):
                label = prop.findtext('b:DisplayName', namespaces=ns)
                if label in ('Name', 'Out Of Scope', 'Reason For Out Of Scope'):
                    print(' ', label, prop.findtext('b:Value', namespaces=ns))
print('Threat count:', len(root.find('m:ThreatInstances', ns)))
PY
```

Use this snippet for inspection only. Generic ElementTree serialization can rewrite
namespace declarations while leaving QName strings in `i:type` unchanged; use a
namespace-preserving editor when writing a model and verify every resulting binding.
